# Chart runtime E2E

This directory owns the compiled runtime contracts for declarative chart behavior. Shared mechanics—Kind lifecycle, Helm and Kubernetes clients, polling, HTTP/TLS clients, redaction, and diagnostics—come from `testkit/e2e`; product assertions stay here.

| Scenario | Make target | Contract |
| --- | --- | --- |
| `fresh-install` (smoke) | `test-e2e-install` | Ordered substrate, manager cache sync and stability, issuer, CSI workload identity, LoadBalancer allocation, and verified ingress edge |
| `n-1-upgrade` | `test-e2e-n-1-upgrade` | Published N-1 certificate/LVM/platform trio → head charts with persisted state, Secret/PVC retention, exact completed Helm-owned provisioner Job, schema ownership, and rollout health; idempotent head reapply without workload rollout; Forge-equivalent apply back to N-1 with state preserved; forward recovery to head |
| `observability` | `test-e2e-observability` | Stack readiness, exact candidate process targets over a valid synthetic Flux tool generation, GPU Operator-compatible DCGM Service discovery through the shipped dashboard namespace-variable and GPU-panel queries, and bounded Prometheus/Loki persistence |
| `observability-tls` | `test-e2e-observability-tls` | Ordered internal CA adopted by the platform; single root authority with every stack/datastore/control-plane leaf chaining to the mounted root; internal-CA/DNS verification for stack servers, self-monitors, Grafana datasources/sidecars, Loki gateway, Promtail, and Alertmanager; verified control-plane edge/backend HTTPS; gateway readiness and mounted CA; rejected plaintext Redis/PostgreSQL transport; root stability across a reconcile |

Static render checks own what does not need a cluster: `scripts/check-dashboards.sh` proves the organized dashboard UIDs/titles/folders and data/storage panel queries, `scripts/check-service-selectors.sh` proves disjoint datastore/exporter Service selection, and `scripts/check-gateway-tls-client.sh` proves the gateway's verify-full/rediss client configuration.

Each runnable scenario declares its Helm inputs as catalogue `renders`: the platform chart with the ordered values files under `test/e2e/values/` (plus repository presets), the certificate substrate, and the LVM substrate with the strings Kind installs. Scenarios install exactly those files; only composed image identities and Kind-derived addresses are layered at runtime. The CI selector templates these renders to decide whether a chart change alters what a scenario installs.

Every target provisions a fresh uniquely named Kind cluster and executes once. There are no scenario retries or accepted flakes. On failure, `testkit/e2e/diagnostics` collects redacted Kubernetes, Helm, describe, and log evidence. CI persists it through `ITERABASE_E2E_DIAGNOSTICS`.

## Fixture modes

Required `source` and `candidate` runs both use the single composer-produced runtime bundle. The composer verifies exact-source temporary or immutable candidate chart archives, the same-recipe companion, selected nested charts, image digests, image archives/references, and checksum-pinned transition inputs before exposing one local platform plus certificate/LVM-substrate composition. After each scenario creates Kind, the common required `import-runtime-images` stage restores every supplied archive, verifies its image-config digest/source label, and transports its exact reference into the new cluster before any predecessor or current Helm install; a runner-daemon load alone is not accepted transport. Workload assertions bind that request reference to the imported single-platform manifest digest reported by CRI rather than comparing it to the distinct config or registry/index digest. Fixture mode changes custody only; source, candidate, and resolved baselines use the same stage DAG and assertions. `published` remains an explicit local compatibility fixture and is not a required PR/candidate route.

The observability scenarios always publish a deterministic in-cluster `GitRepository` artifact fixture through the same source-controller hostname contract used by the materializer. When a selected tool-runner image is present, Helm readiness proves that exact composed identity can verify, load, and register the valid generation instead of waiting on an intentionally absent source. Before any platform data claim or composed harness `AgentPool`, both observability DAGs call the shared Kind substrate helper. It removes Kind's local-path namespace/default class, prepares a real loop-backed thick `iterabase-data` VG in the single privileged node, installs the exact composed `lvm-storage-substrate`, and verifies OpenEBS CRD/controller/node/CSI/VG readiness plus exactly `iterabase-lvm-xfs` and `iterabase-agentpool-lvm-xfs`. It never substitutes Kind's default `local-path`/`standard` class.

The N-1 upgrade receives its baseline from the workflow and never discovers it: `ITERABASE_E2E_N1_{CERT_MANAGER,LVM_STORAGE,PLATFORM}_REFERENCE` are exact `oci://…/<chart>:<version>` references sharing one published version, `ITERABASE_E2E_N1_*_SHA256` are the lowercase SHA-256 checksums of the pulled archives, and optional `ITERABASE_E2E_N1_*_ARCHIVE` supply already-pulled archives. Missing, floating, mismatched, or non-canonical inputs and any checksum mismatch fail the scenario before installation. The head chart may equal but never precede the baseline version.

`make test-e2e-unit` runs the compiled hermetic scenario and intentional break fixtures for the N-1 baseline contract and archive checksum, manager cache-sync detection, ambiguous duplicate CRDs, Secret/PVC/all-stable-workload and completed provisioner Job identity retention, incorrect rollback revision/status/chart history, candidate tool-artifact integrity, disabled-component readiness, bounded historical persistence samples, declared render inputs, and plaintext self-monitoring without provisioning infrastructure.
